# Query Changes and Optimizations

Applies when a query is rewritten, for speed or otherwise, and is meant to select the same rows as before.

## Prove the new query returns the same rows

Compare the old and new result sets on the same data before merging, with a test or by running both against the same database, and put the result in the PR description. Compare the rows, not only the totals: on a large table such as `orders` or `wallet_transactions`, a rewrite can lose rows without the count moving noticeably. For paginated endpoints, compare `total()` and the row order, not just the first page.

## Call out any condition change

If the rewrite adds, removes or changes a `WHERE`, `JOIN`, `EXISTS`, `HAVING` or `ORDER BY` condition, say so in the PR description. The reviewer should treat it as a behavior change, not as part of the optimization.

## No index hints

Never use `FORCE INDEX`, `USE INDEX` or `IGNORE INDEX`. They are MySQL-only and break on PostgreSQL (see Portable SQL in `architecture.md`). If a query needs an index, add it with a migration generated by `php artisan make:migration` (see `generators.md`) and let the planner choose it.
